Architecture Decision Records capture choices that are expensive to reverse, along with the
context that made them right at the time. The point is not the decision — it is that a
contributor arriving in two years can tell whether the reasoning still holds.

## ADR-0001 in one paragraph

TypeScript end-to-end in a pnpm + Turborepo monorepo: React + Vite for an offline-capable PWA,
Fastify + tRPC for the API, Postgres 16 + Drizzle, pg-boss for jobs, MinIO for object storage,
better-auth for sessions. Three constraints drove almost all of it — solo-founder velocity,
contributor accessibility, and a self-host footprint a volunteer can run. That last one is why
the queue lives inside Postgres instead of Redis, and why there is no SSR framework.

Read the [full record](https://github.com/saintparish4/pyra/blob/master/adr/0001-stack-choice.md)
for the alternatives considered and the accepted risks.

## Format

Each record carries: **Context** (the constraints in force), **Decision** (what was chosen, per
component, with the alternative it beat), **Consequences** (positive, and the negatives
accepted knowingly), and **Revisit triggers** — the specific conditions that would reopen the
decision.

Revisit triggers are the part that earns the format. "Reconsider Next.js if a public,
SEO-relevant surface becomes a goal" is a decision that can be checked against reality later;
"we chose Vite" is not.

## When to write one

When a choice is costly to undo, constrains later choices, or will otherwise be re-litigated
by someone who wasn't there. Library picks generally don't qualify. Anything that shapes the
deployment footprint, the data model, or the tenancy boundary does.

Number sequentially, never renumber, and never delete: a superseded ADR gets its status
changed and a pointer to the record that replaced it. The history is the value.

## ADR-0002 through 0005 in one paragraph each

**0002 — Incident storage.** `incidents` gets first-class SQL columns for everything Pyra
queries on, plus a `payload jsonb` holding the NERIS-shaped incident, validated by the
generated zod schema on every write. 464 component schemas are reachable from the incident
payload roots and upstream is still moving them; mirroring that into tables would make every
NERIS release a multi-table migration. The cost is no referential integrity inside the payload
and harder analytics, and the mitigation is a standing rule — promote a field to a real column
the moment we filter or join on it.

**0003 — Tenancy.** The API connects as a non-owner `pyra_app` role; every domain table gets
`ENABLE` + `FORCE ROW LEVEL SECURITY` with policies keyed on `current_setting('app.department_id')`,
and a `withTenant()` helper is the only way to set it. Application-level scoping works until one
query forgets, and that failure is a silent cross-tenant leak. The carve-out is written down:
better-auth queries the four auth tables with no department in scope, so RLS there would break
sign-in — tenancy on those is enforced in procedure code and proven by integration tests.

**0004 — `@pyra/neris` is generated.** An in-repo generator reads the local NERIS checkout and
emits zod schemas, value sets, and the NFIRS crosswalk into `src/generated/`, and that output is
committed so a dictionary bump arrives as a reviewable diff. Runtime validation has to work
offline in the browser, which rules out types-only generators. The revisit trigger is explicit:
over ~600 lines of generator, or any hand-patched output, and we switch to `openapi-zod-client`.

**0005 — Imports are records.** Imported legacy incidents carry `source = 'nfirs_import'` or
`'vendor_import'` and never enter the NERIS submission pipeline. NERIS takes current incidents;
a 1987 structure fire is the department's own record — stored, searchable, exportable, with the
original row preserved verbatim. It is the difference between "import forty years of history"
being a two-week feature and a compliance catastrophe.
