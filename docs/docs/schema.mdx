Pyra's data model has two layers: our own tables, which exist and are migrating; and the NERIS
incident model, which is published upstream as reference material but not yet implemented.

:::info Stub

The auth, tenancy, and audit tables are real, and so is the generated NERIS dictionary. The
incident model itself is not — see below.

:::

## Layer 1 — Pyra's tables

Drizzle ORM over Postgres 16, in `packages/db`. SQL-first on purpose: migrations and
row-level-security policies stay readable as SQL, and a contributor can review them without
learning an ORM's dialect.

| Table | Purpose |
| --- | --- |
| `departments` | The tenant. `id` (uuid), `name`, `slug` |
| `users` | Members. Belongs to exactly one department; carries `role` |
| `sessions`, `accounts`, `verifications` | better-auth's tables, in our own database |
| `audit_log` | Append-only record of every mutation: department, actor, entity, action, before/after |

Auth tables live in our Postgres rather than a vendor's, which makes migrating off better-auth
a data-preserving refactor instead of a data migration.

Two Postgres features are load-bearing and drove the choice of database:

- **Row-level security** for department isolation on a shared instance. Domain tables carry
  `ENABLE` + `FORCE ROW LEVEL SECURITY` and a policy keyed on `current_setting('app.department_id')`;
  the API connects as a non-owner role so the policies bind it. The policies live in readable
  SQL at `packages/db/sql/tenancy.sql`, applied by `pnpm --filter @pyra/db harden` after every
  migration, because drizzle-kit does not model roles, grants, or `FORCE`.
- **JSONB** for imported records that don't map 1:1 onto NERIS — preserved verbatim, still
  searchable — and for absorbing NERIS schema versions without a migration per revision.

## Layer 2 — shared DTOs

`packages/shared` holds the zod schemas both the API and the web app validate against: auth
DTOs, the API error envelope, and branded ID types. `DepartmentId` is branded so a bare string
cannot be passed where a tenant scope is expected — the compiler forces every value through a
parse at the boundary, which is a cheap structural defence against cross-tenant bugs.

## Layer 3 — NERIS

`packages/neris` is **generated**, and the output is committed.

The published framework lives upstream at
[`ulfsri/neris-framework`](https://github.com/ulfsri/neris-framework). Contributors clone it to
`NERIS/` at the repo root, which is gitignored — it is upstream's to version, and a copy in
our tree would go stale without anyone noticing:

| Path | Contents |
| --- | --- |
| `CORE/modules/yml/` | Field metadata for dispatch, entity, and incident modules |
| `CORE/value_sets/yml/` | 96 value sets as `CAPITAL_CASE` enums |
| `SECONDARY/` | Community Risk Reduction, Incident Analysis, Health & Safety — still moving upstream |
| `MAPPINGS/` | NENA CLDXF location mapping; dispatch-code → incident-type template |
| `openapi.json` | OpenAPI 3.1.0, NERIS v1.4.78, against the test API |

`pnpm --filter @pyra/neris generate` turns those into checked-in TypeScript: zod schemas for
the incident payload subgraph, every value set as an enum with its human labels, the NFIRS
crosswalk as data, and the spec version and digest. Committing the output means a dictionary
bump arrives as a **reviewable diff** rather than as a silent build-time change.

Three things the dictionary will surprise you with:

- **The API and the value-set YAML disagree, and the API wins.** The spec carries 130 incident
  types where the YAML has 128, and fixes the YAML's typo `BACKOUNTRY_RESCUE`. Membership comes
  from `openapi.json`; labels come from the YAML. Both directions of the disagreement are
  reported during generation.
- **Types are variable depth.** `LAWENFORCE` has one level, `MEDICAL||ILLNESS` two,
  `FIRE||OUTSIDE_FIRE||TRASH_RUBBISH_FIRE` three. A picker that assumes three is wrong for a
  third of the dictionary.
- **The NFIRS crosswalk is not a function.** 161 of its 164 codes map to more than one NERIS
  type, and code `300` maps to 53. It is typed as arrays, always, so an importer cannot quietly
  take the first candidate — which is why importing history needs a human mapping-review step.

A scheduled CI job fetches the live spec and fails on drift, so "regeneration is due" arrives as
a notification rather than as a mysterious validation failure months later.

What remains blocked on NERIS enrollment is *submission*, not modelling: production API access,
an integration credential, and a department's entity ID.

## Not written yet

- The `incidents` table itself. The shape is decided —
  [ADR-0002](https://github.com/saintparish4/pyra/blob/master/adr/0002-incident-storage.md):
  first-class columns for everything queried on, plus a `payload jsonb` validated by the
  generated schema on every write — but it is not built.
- **The conditionality layer.** Generated schemas give shape; NERIS's conditional requirements
  (`possible_if`, `neris_core_if`, and rules that exist only in OpenAPI `description` strings)
  are written as inconsistent prose and have to be hand-written as named rules. This is where
  the test pyramid is deliberately heaviest.
- The full-export format — the "own your data" guarantee needs a documented, open shape.
